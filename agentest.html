Summary: Specification-driven testing for tool-using LLM agents: business rules are mined from the system prompt, tool definitions and LLM domain knowledge, refined into Given–When–Then specifications, and each specification drives the environment setup, simulated user and interaction used to test it. On τ²-bench it exposes violations of 89 and 121 distinct specifications on two underlying models, 3.4× and 2.5× as many as all baselines combined.

Sources:

  • Quan et al. - 2026 - AgenTest Mining Business Rules to Test LLM Agents.pdf (arXiv:2610.28116v1, 20 Oct 2026)

Last updated: 2026-10-26

Problem

Tool-using agents (customer-service agents that modify orders, refund, cancel, update records through backend APIs) must obey business rules about when an action is allowed and which data it may touch. In conventional software those rules live in code (authorization checks, validation, data constraints). In an agent they are spread across the system prompt and tool definitions, or remain implicit in domain knowledge, so a rule can be followed in one conversation and broken in another. (source: Quan et al. 2026)

The paper’s motivating example: a user asks the airline agent to add a checked bag to a reservation that belongs to a different user. The agent updates the reservation, charges the other user’s card and reports success. The run ends in a valid state and satisfies the request, but violates “a reservation may be modified only at the request of its owner” — a rule no single artifact states (the prompt requires user identification; the tool accepts a reservation ID). A predefined functional test catches it only if someone already anticipated the rule, built the scenario and supplied an oracle. (source: Quan et al. 2026)

Existing agent testing falls into two groups the paper contrasts itself with: security-oriented work (jailbreaks, prompt injection, malicious tool use) and predefined-task benchmarks such as τ²-bench, which need the behavior and the judging criterion specified in advance. (source: Quan et al. 2026)

Approach

Definitions: an agent is A = (M, π, T) (model, system prompt, tools); a business-logic bug is a pair (specification s, trace τ) where the preconditions of s hold in τ but the observed behavior violates its postconditions. (source: Quan et al. 2026)

Stage 1: mining and refinement of specifications

  • Tool-based extraction: an LLM reads tool schemas and docstrings for argument constraints (formats, ranges, enumerations, relations between arguments) and ordering constraints (tool B needs an output only tool A produces). A second LLM check drops an ordering dependency when the user could supply the value directly.
  • System-prompt extraction: the LLM reads the whole prompt and returns each rule with a supporting quotation and the tools it constrains. Two repair passes follow: a passage-coverage check (uncited passages are re-assessed as “no rule”, “extra evidence” or “missing rule”) and a tool-binding check (a rule such as “confirm before any reservation update” may apply to tools beyond the section it appears in). Each proposed binding needs a quotation that is verified against the source.
  • Domain-knowledge inference: per tool, along four dimensions — argument constraints, environment-state constraints (the object exists, belongs to the requester, is in a permitting state), ordering constraints, behavioral norms — plus three cross-call patterns (a call invalidates later operations, effects accumulate past a limit, a closed resource may not be used again).
  • Deduplication and filtering: an LLM groups specifications constraining the same operation and keeps the one from the most reliable source (schema over prompt over domain knowledge). A second layer removes domain-knowledge rules the agent cannot violate: the LLM must point to the field, prompt sentence or tool parameter that defines every limit or status the rule relies on, and code verifies the pointer exists.
  • Refinement: a condition is split into a disjunction of alternatives C = C₁ ∨ … ∨ Cₙ, each a conjunction of atomic conditions. Each alternative yields one permitted scenario. Prohibited scenarios come from the negation of the whole condition (¬C), because a state that fails only one alternative may still satisfy another and would not exercise the prohibition. Each scenario is encoded as Given (applicable conditions) / When (the triggering request, without prescribing the agent’s response) / Then (required, prohibited or permitted behavior). The paper’s cancellation example: four alternative eligibility conditions give four permitted scenarios and two prohibited ones.

Stage 2: specification-driven testing

  • Test driver: Given is split into atomic clauses of three kinds — environment conditions, user-side conditions, ownership relations. Environment clauses are mapped to ⟨table, field, operator, value⟩ tuples validated against the data model; the driver searches for objects satisfying them (following foreign keys), pairing an object with its owner or another user as the ownership relation requires. If no object qualifies it edits an object’s constrained attributes and re-verifies. A specification is not tested if its precondition cannot be established (e.g. it refers to an expired reservation and the data model has no such status). A simulated user is configured with the requester’s ID, the object IDs, the goal task derived from When, and the user-side conditions to convey; for another user’s object it is not given the owner’s private information.
  • Interaction strategies: refined specifications fall into 13 structural categories according to the text (the paper’s Table 1 lists 14 rows summing to the 67 strategies: state precondition, quantity limit, step order, confirmation, conditional permission, prohibition, transfer, object ownership, disclosure, argument value, procedure completeness, communication protocol, truthful statement, argument content). For each, the authors enumerate ways a user can vary the timing, form, completeness and framing of the information the constraint depends on, giving a domain-independent library of 67 strategies (examples: “fail a condition by a narrow margin”, “request an action on another user’s object”, “reveal an over-limit item only when asked”). A default strategy (state task, supply known facts, confirm when asked) is used outside the library.
  • Bug experience memory: strategies that exposed violations are promoted, repeatedly unsuccessful ones demoted, untried ones stay candidates. Generated cases are checked (tool and object references, state changes applied in a fresh environment, the proposed compliant tool sequence replayed) and dropped if setup is invalid.
  • Hybrid oracle: assertions are extracted from the Then of the target specification and of other applicable specifications on the same tools, before execution, so the criteria cannot adapt to the outcome. Constraints on arguments, state and event order become executable predicates over tool calls and states. Conversational constraints stay natural-language assertions judged by an LLM that must return supporting quotations; quotations are checked against the trace and an unsupported judgment leaves the assertion undecided.

Evaluation setup

  • Agents: τ²-bench airline, retail and telecom agents (15, 17 and 13 tools; telecom adds 30 user-side tools), each on two underlying models, DeepSeek-V4-Flash and Qwen-3.8-Flash.
  • Baselines: the τ²-bench task set (278 hand-written tasks: 50/114/114, judged by final database state and a few required actions); IntellAgent (policy-combination scenario generation with an LLM judge; run on airline and retail only because it does not support telecom’s user tools); MANTRA (SMT-validated compliance tasks; released suites of 44/57/31 tasks; single scenario message, no simulated user).
  • Configuration: GPT-4.1 for specification extraction, Claude Opus 5.5 for test synthesis and LLM judgments, DeepSeek-V4-Flash for the simulated user. Specifications are mined once per domain and both models are tested against the same ones. Three rounds: round 1 runs each refined specification once with the default behavior; rounds 2–3 each apply one strategy perturbation per specification.
  • Bug counting: two authors independently review every AgenTest run and every violation a baseline reports; only confirmed violations count. Bugs are deduplicated by the refined specification they break, so a “bug” is a violated refined specification, however many runs violate it. One rule is excluded for all approaches — the agent must not send a message and call a tool in the same turn — because agents break it in 69.3% (DeepSeek) and 32.2% (Qwen) of default-strategy test cases regardless of the specification under test.

Results

Specification quality (RQ1)

Mining yields 483 specifications (214 from the system prompt, 109 from tool definitions, 160 from domain knowledge); deduplication removes 120, binding repair adds 25 and filtering removes 19, leaving 369, which refinement turns into 551 refined specifications. 88.0% are correct (Cohen’s κ 0.88): 100% of those from tool definitions, 91.2% from the system prompt, 80.6% from domain knowledge. Of the 66 incorrect ones, 30 state rules with no support in the source, 19 contradict the prompt or tool documentation, 17 drop a condition of the rule. Tool definitions and domain knowledge supply 56% of the filtered specifications. (source: Quan et al. 2026)

Bug detection (RQ2)

Baselines combined find 26 and 49 bugs, so AgenTest finds 3.4× and 2.5× as many; 83 and 97 of its bugs are found by no baseline. AgenTest finds 6 and 24 of the baseline bugs, which leaves 20 and 25 found only by a baseline (derived from the figures in the paper). Every baseline-only bug breaks a specification AgenTest also tests but arises in a long task chaining several goals (e.g. troubleshooting several faults before a transfer, or booking and requesting compensation in one conversation); AgenTest tests one specification at a time and does not reproduce those interactions. At equal budgets AgenTest leads beyond 44 runs (DeepSeek) and 178 runs (Qwen); below that IntellAgent finds slightly more because its few bugs recur in many conversations (its most frequent appears in 41 and 93 of them). (source: Quan et al. 2026)

Component effectiveness (RQ3, DeepSeek-V4-Flash)

  • Drivers are constructed for 504 of 551 refined specifications (91.5%); the other 47 are 26 incorrect specifications and 21 requiring a state the environment cannot hold (e.g. a ported-out line). In 1,503 of 1,512 runs (99.4%) the simulated user states the Given conditions and triggers When.
  • Interaction strategies account for most bugs: the default strategy alone violates 6 refined specifications, random strategy selection 84, AgenTest (with bug experience memory) 89 (bug rate 1.2%, 6.9%, 7.7% of runs).
  • The hybrid oracle agrees with the manual review on 1,476 of 1,512 runs (97.6%) with precision 82.6% (161 of 195 reported violations), rising to 90.4% in library-strategy runs. The judges of the baselines reach 25.0% (τ²-bench), 46.5% (IntellAgent) and 5.7% (MANTRA) precision on the same measure. In default-strategy cases 492 of 579 checks (85%) are deterministic rules on tool calls and states. (source: Quan et al. 2026)

What the bugs are (RQ4)

Symptom × model (DeepSeek / Qwen): invalid argument 43 / 46; disallowed operation 13 / 22; missing prerequisite 12 / 25; unauthorized action on another user’s object 9 / 10; improper escalation 6 / 10; incorrect communication 6 / 8. The four symptoms involving tool calls on business data make up 86.5% and 85.1% of bugs. Root cause: the rule is implicit (stated in no artifact) for 50.6% / 36.4% of bugs, stated but ignored for 30.3% / 26.4%, stated but misapplied for 19.1% / 37.2%. Unauthorized actions come almost entirely from implicit rules (8 of 9 and 9 of 10); missing prerequisites only from stated rules. Only AgenTest exposes agents acting on another user’s object, a situation a test has to construct deliberately. (source: Quan et al. 2026)

About 60% of bug-triggering runs (60% and 59%) cannot be detected from the final state alone: 42% and 37% leave the database unchanged, and the rest write a state a compliant run could also produce (acting on another user’s reservation, acting without an explicit yes). (source: Quan et al. 2026)

Takeaways stated by the authors

  • An implicit-rule bug is a defect of the agent as a whole (prompt plus tools plus model), not necessarily of the model; the repair may be stating the rule in the prompt or enforcing it in the tool.
  • Rules with structured evidence (ownership, argument values, call order) need not be left to the model; the same deterministic predicates could guard tool execution at runtime (they cite Kamath et al. 2025). Conversational rules such as confirmation stay with the model and testing remains their main safeguard.
  • Decomposing a request into single-goal subtasks may reduce interference between goals, provided rules spanning subtasks (e.g. a compensation limit per incident) are enforced across them.
  • Bugs depend on the underlying model (misapplied-rule bugs: 17 on DeepSeek vs 45 on Qwen), so one model’s results do not transfer. Specifications depend only on the prompt and tools, so they can be mined once and rerun as a regression suite when the model is upgraded.

Limitations

Stated by the authors: three domains of one benchmark and two underlying models; AgenTest needs the system prompt, tool definitions and a resettable environment with a known data model; the interaction strategies are untested in unseen domains; testing one specification at a time misses multi-goal interactions; domain-knowledge specifications are the least reliable (80.6% correct). (source: Quan et al. 2026)

Bug counts are per violated refined specification, and two authors reviewed every AgenTest run and every reported baseline violation (see the bug-counting description above). The code is released at an anonymized repository link given in the PDF. (source: Quan et al. 2026)

Relation to the rest of the wiki

AgenTest is the instance in Specification-Based Testing where the specification is inferred rather than provided, and where the specification-to-test step is automated rather than manual. Its oracle design — assertions fixed before execution, deterministic where evidence is structured, LLM judgments that must quote the trace — is a concrete answer to the second-order oracle problem raised in The Oracle Problem and LLM-as-Judge Evaluation. The deterministic-check share (85%) bears on Runtime Enforcement. The unauthorized-action and prerequisite bugs are agent-level failures of the kind catalogued in Agent Failure Modes and Agent Safety; the simulated user belongs with the multi-turn testing in SWE-DIVE and MORTAR.
