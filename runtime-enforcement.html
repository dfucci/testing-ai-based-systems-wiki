Summary: Runtime enforcement intercepts LLM agent actions during execution and applies predefined safety constraints before those actions take effect, as opposed to pre-execution risk estimation or post-hoc evaluation.

Sources:

  • Wang et al. - 2025 - AgentSpec Customizable Runtime Enforcement for Safe and Reliable LLM Agents.pdf

Last updated: 2026-08-30

Motivation

LLM agents can deviate from user intent at runtime in ways that are hard to predict statically. Pre-execution risk assessment (e.g., LLM-based sandboxes) can identify potential risks but offer no enforcement mechanism and are susceptible to adversarial manipulation. Post-hoc evaluation identifies failures after damage is done.

Runtime enforcement is the active middle layer: monitor execution as it happens, intercept at decision points, apply constraints.

Core Architecture

A runtime enforcement system needs:

  1. Event monitoring: detecting when relevant actions are about to occur
  2. Predicate evaluation: checking whether the current state satisfies safety conditions
  3. Enforcement: modifying or halting execution when constraints are violated

AgentSpec Approach

AgentSpec implements runtime enforcement via a DSL. Rules specify:

  • trigger: which events activate the rule
  • check: predicates that must hold for enforcement to apply
  • enforce: what to do when rule fires (stop, userinspection, llmselfexamine, invokeaction)

Integration point: the LangChain iter_next_step function, which is intercepted before each agent action executes. Three hook points: AgentAction, AgentStep, AgentFinish.

Enforcement Strategies

Hard stopping (stop)

Terminate execution immediately. Appropriate for clearly dangerous actions (e.g., pouring onto non-wettable objects, running destructive shell commands).

Human-in-the-loop (user_inspection)

Pause and request human approval. Appropriate for high-stakes actions that are context-dependent (e.g., financial transfers, sensitive file access).

LLM self-reflection (llm_self_examine)

Invoke the agent’s own reasoning to generate a corrective response. Appropriate when the right action is context-dependent and an LLM can determine the safe alternative.

Corrective action (invoke_action)

Execute a predefined alternative action. Appropriate for domain-specific responses where the safe alternative is known (e.g., adjusting following distance when vehicle detects obstacle).

Overhead

AgentSpec demonstrates runtime enforcement is computationally feasible:

  • Parsing: ~1.42 ms
  • Predicate evaluation: ~2.83 ms (code), ~1.11 ms (embodied)
  • Negligible relative to agent execution time (25.4s code agents, 9.82s embodied)

(source: Wang et al. - 2025 - AgentSpec)

Relationship to Other Verification Approaches

Approach When Mechanism
Runtime enforcement During execution Intercept + constrain
Trajectory diagnostics (TRAJEVAL) During/post execution Observe + diagnose
Static analysis Pre-execution Analyze code structure
Formal verification (Lean4Agent) Pre-deployment (spec) + post-execution (trajectory) Prove workflow properties in Lean4; localize failures against a formal assumption

Runtime enforcement and trajectory analysis are complementary: trajectory signals can inform what rules to write; enforcement prevents known failure modes. Lean4Agent is a design-time complement rather than a runtime one: it proves properties of the workflow specification before execution runs at all, then localizes trajectory-level failures afterward — see Formal Verification of Agent Workflows.

Limitations

  • Deterministic enforcement only — cannot reason about long-term consequences of safe-seeming immediate actions
  • Rules must be manually specified or LLM-generated (LLM generation: ~95% precision but only ~71% recall)
  • Cannot prevent failures that don’t trigger defined events
