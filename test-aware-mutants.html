Summary: Giving an LLM the existing base tests alongside the code, and asking it for a subtle bug that still passes those tests, raises the rate of verified faults from 12.2% (test-blind) to 87.8% on HumanEval in a single prompt — far above the rule-based tool mutmut (4.4%).

Sources:

  • Kiele et al. - 2026 - Beyond Rule-Based Mutation Testing Test-Aware Mutant Generation Using Large Language Models.pdf (ESEM 2026, LIPIcs 49:1-49:20)

Last updated: 2026-10-18

Idea

Prior LLM-based mutant generators (LLMorpheus, BugFarm, µBERT, LEAM) are test-blind: the model sees only the source code, so it cannot target what the existing tests already cover and often produces mutants that the base suite kills trivially or that are equivalent to the original. Kiele et al. frame mutant generation as an adversarial task: given the problem statement P, canonical solution C and base tests Tbase, produce a mutant C’ that keeps the function signature, passes Tbase, and fails at least one test of a hidden oracle Toracle. One mutant per problem/model/prompt, no compilation or execution feedback. (source: Kiele et al. 2026)

Setup

  • Benchmarks: EvalPlus-extended HumanEval (164 problems) and MBPP (378 problems). Base tests are the original developer-style tests (7.7 per HumanEval problem, 3 per MBPP problem); the extended EvalPlus suites (80× and 35× more tests) act as an automated oracle, so a mutant that passes the base tests but fails an extended test is a verified, non-equivalent fault without manual review.
  • Four mutually exclusive outcomes: Invalid (does not compile / times out), Rejected (killed by a base test), Success (survives base, caught by oracle), Undetected (survives both).
  • Models (temperature 0): Gemini 3.1 Pro, Gemini 3 Flash, GPT 5.1 Codex Mini, GPT 4.1 Mini, Qwen3-32B.
  • Prompts: two families × test-aware (ta) / matched test-blind (tb), differing only in whether base tests are shown. agent1 is free-form (analyze blind spots → plan minimal mutation → mentally dry-run against each base test); agent2 forces a fixed template (function summary, base-test coverage, 2-3 blind spots, mutation plan, per-test trace).
  • Baseline: mutmut with default settings — exhaustive, ~17.6 mutants per HumanEval task and ~9.2 per MBPP task (2,841 and 3,427 mutants in total).

Results

Effectiveness

Success rate with agent1-ta vs. agent1-tb (Gemini 3.1 Pro): HumanEval 87.8% (144/164) vs. 12.2% (20/164), MBPP 79.1% (299/378) vs. 23.0% (87/378) — up to a 7× gain. mutmut reaches 4.4% (126/2,841) on HumanEval and 5.7% (195/3,427) on MBPP; almost every LLM configuration beats it, even test-blind (exceptions: agent2-tb with Gemini 3.1 Pro at 4.3% and GPT 4.1 Mini at 3.0% on HumanEval). GPT 5.1 Codex Mini goes from 11.6% to 81.1% (agent1) and 7.9% to 82.3% (agent2). Even the weakest model, GPT 4.1 Mini, improves from 5.5% to 31.7% (agent1). The shift is from Rejected to Success: without seeing the tests, models make changes the base assertions already catch. (source: Kiele et al. 2026)

Model capability matters more than prompt wording for the Invalid rate: the smaller models (Qwen3-32B, Gemini 3 Flash, GPT 4.1 Mini) produce more non-compiling mutants. The free-form agent1 generally beats the structured agent2; e.g. GPT 4.1 Mini under agent2-ta has Rejected mutants on 156 tasks (48 HumanEval, 108 MBPP) where agent1-ta evades the base tests. The authors read this as forced explicit blind-spot enumeration hurting the adversarial search for smaller models.

Subtlety — no clear difference

Subtlety is the oracle kill rate: the fraction of extended tests a mutant fails (lower = narrower fault). Test-aware medians sit around 10-30%, comparable to test-blind, and the paper states it is “not clear” that LLM mutants are more or less subtle than mutmut’s. The gain from test-awareness is therefore yield at comparable subtlety, not subtler bugs. (source: Kiele et al. 2026)

What the “Undetected” mutants are

For the best setting (Gemini 3.1 Pro, agent1-ta) all 65 Undetected mutants (9 HumanEval, 56 MBPP) were hand-labeled by one author:

Class Count
Equivalent — identical/cosmetic 1
Equivalent — semantic refactoring 5
Equivalent — out-of-specification fault 3
Equivalent — dead code 0
Non-equivalent — true oracle gap 49 (75.4%)
Non-equivalent — ambiguous (under-specified task) 7 (10.8%)

So only 9 of 65 (13.8%) were genuine generator failures; most “survivors” were real edge-case bugs EvalPlus never tests (e.g. HumanEval #18 never tries an empty substring). The oracle used to score the method is itself incomplete — a ceiling on the reported success rates rather than an inflation of them. (source: Kiele et al. 2026)

Cost

Per generated candidate, an LLM mutant is roughly 7-12× slower than a mutmut mutant (GPT 5.1 Codex Mini agent1-ta: 29.7 s/problem on HumanEval, 16.4 s on MBPP, vs. ~2.4 s per mutmut mutant). Per verified fault the ranking reverses: 36.6 s (HumanEval) and 22.5 s (MBPP) for the LLM vs. 54.0 s and 41.9 s for mutmut. Test-aware prompting is also cheaper in tokens per verified mutant than test-blind for every model except GPT 4.1 Mini, because fewer generations are wasted. (source: Kiele et al. 2026)

Iterative prompting narrows the gap

Allowing up to two retries with execution feedback (error message for Invalid, the failing base-test I/O for Rejected, “try a different approach” for Undetected) lifts Gemini 3.1 Pro agent1-tb from 12.2% to 83.5% and agent1-ta to 98.2% (161/164); agent2-ta reaches 99.4% (163/164, from 130). Test-aware needs far fewer attempts (1.19-1.24 per HumanEval problem vs. 2.27-2.46 for test-blind). Single-shot test-awareness captures most of the achievable gain; iteration converts the remaining 10-15%.

Caveats and source inconsistencies

  • Internal discrepancy: the abstract reports a 87.7% HumanEval verified-fault rate; the body text and Table 4 give 87.8% (144/164). This page uses 87.8%.
  • One mutant per task at temperature 0; the authors note temperature 0 does not guarantee exact reproducibility.
  • The 65-mutant manual classification was done by a single author; no inter-rater agreement was measured.
  • Python, self-contained benchmark functions only; base-test quality was not varied, so how the gain depends on suite strength is untested. EvalPlus is a proxy oracle — real settings have none, so surviving mutants should be read as suggestions for new tests, not validated defects.
  • The authors hypothesize that LLMut (Wang et al. 2026) found test-inclusive prompts slightly worse because it appended tests as passive context rather than framing the task adversarially. This explanation is the authors’ conjecture and was not tested in the paper (needs verification).

Relation to broader wiki

Adds a third LLM-era role for mutation testing alongside intent-based mutant generation and mutation-guided assertion feedback: generation conditioned on the existing test suite, so the mutants specifically probe that suite’s gaps. See Mutation Testing for LLM Systems. The 49/65 true-oracle-gap finding is another instance of the lesson in The Oracle Problem and Auditing Feedback-Driven Evolution: a stand-in oracle (here EvalPlus’s extended tests) is weaker than assumed, though here the weakness understates the method rather than inflating it. Its Success definition (survives the base tests, caught by an oracle) is a mutant-side analogue of the potential-vs-effective split in Oracle Conversion.
