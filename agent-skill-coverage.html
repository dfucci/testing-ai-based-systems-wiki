Summary: A test adequacy criterion for LLM agent “skill” documents — measuring whether documented behavior constraints were exercised with observable evidence during agent trajectories, independent of whether the underlying task succeeded.

Sources:

  • Tan et al. - 2026 - Skill Coverage A Test Adequacy Metric for Agent Skills.pdf

Last updated: 2026-10-18

The gap this fills

This wiki previously noted (in Test Adequacy Criteria for ML Systems, citing Tangent) that no accepted test adequacy standard exists for LLM-based agent systems — practitioners lean on post-deployment observability instead of a principled “have we tested enough” criterion. Skill Coverage (Tan et al. 2026) is the first concrete adequacy criterion purpose-built for one specific agent artifact: the skill document (a reusable procedural-knowledge specification that guides an agent across tasks). (source for the gap: Pan et al. 2026; for the criterion: Tan et al. 2026)

What it measures, and what it deliberately doesn’t

Skill coverage extracts observable behavior constraints from a skill document, then reports a binary cover/not-cover judgment per constraint based on whether an agent trajectory provides sufficient observable evidence it was exercised. It explicitly does not attach a pass/fail correctness label to each constraint — that decouples “was this tested” from “did the agent do it right,” mirroring the same decoupling code-coverage tools make between “was this line executed” and “is this line correct.” (source: Tan et al. 2026; the code-coverage analogy is this wiki’s gloss)

This decoupling is what exposes the core finding: on SkillsBench, task-level success routinely coexists with only 39.90-43.98% of documented skill behavior actually being exercised. A benchmark can look thoroughly tested by its pass rate while leaving most of a skill’s documented guidance completely unverified. (source: Tan et al. 2026)

Relation to other adequacy criteria in this wiki

Criterion Object under test Signal
Neuron coverage / surprise adequacy The trained model’s internal activations Structural coverage of decision space
MR-compliance (e.g. METTLE) The system’s behavior under transformation Violation rate against defined relations
Skill coverage A skill document (procedural spec, not code or weights) Binary evidence of exercised behavior constraints

Skill coverage is unusual among these in targeting a natural-language artifact (the skill spec) rather than code, weights, or transformed inputs — closer in spirit to requirements coverage in traditional software testing than to any ML-specific adequacy criterion.
