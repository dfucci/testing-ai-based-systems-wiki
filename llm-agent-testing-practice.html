Summary: Three independent empirical studies — one mining 2,572 real GitHub agent tests, one observing student teams building LLM apps, one coding QA artifacts across 157 open-source agent repos — converge on the same picture: agent testing in practice is shallow, source-code-centric, and almost never exercises adversarial, boundary-crossing, or agent-specific failure modes.

Three studies, converging findings

Tangent (Pan et al. 2026) mined 1,190 GitHub repos using LangChain/LangGraph/MCP down to 2,572 manually labeled tests across 240 modules, plus structured interviews with 10 senior industry practitioners. Magalhães et al. 2025 ran a qualitative case study on 99 student reflection reports from 21 team projects building real LLM-integrated apps. Dai et al. 2026 coded repository-visible QA artifacts (not just tests) across 157 popular open-source agent projects against a four-layer execution-surface/safeguard/testing/risk-scenario rubric. Different methods, same conclusions (source: Pan et al. 2026; Magalhães et al. 2025; Dai et al. 2026):

  • Testing stays rooted in source code. Both studies find developers debug and test LLM components the way they’d test any backend code (parsing, API integration), not via model-behavior-specific methods. (source: Pan et al. 2026; Magalhães et al. 2025)
  • Unit-level dominates, integration is rare. Tangent: 61.8% unit-level tests, only 3.5% multi-tool, 0.1% API-level (source: Pan et al. 2026). This mirrors the integration-testing gap Riccio et al. 2020 found in ML testing generally (source: Riccio et al. 2020) — see ML-System Testing Levels.
  • Reasoning and non-functional requirements are barely tested. Tangent: only 8.7% of assertions target reasoning behavior (usually just checking presence, not correctness), and only 7.5% of tests address NFRs at all (security 49%, performance 33.5%, memory 8.8%, policy 4.6%). (source: Pan et al. 2026)
  • No accepted adequacy standard. Tangent’s interviewees explicitly say there’s no metric for “have we tested this agent enough” and rely instead on post-deployment observability/tracing (OpenTelemetry, LangSmith, Langfuse) rather than formal test suites. (source: Pan et al. 2026)
  • Hybrid, tolerance-based strategies fill the gap. Magalhães et al.: teams combine manual exploratory testing, ad hoc testing, and automated unit/integration tests with qualitative, tolerance-based pass criteria — because non-determinism and the oracle problem make strict assertions unworkable. (source: Magalhães et al. 2025)
  • Test data is often trivial. Tangent: 39.9% of tests use placeholder “dummy” data (e.g., literal strings “test1”/“test2”) rather than realistic inputs. (source: Pan et al. 2026)
  • Adversarial/boundary testing is nearly absent at repo scale. Dai et al.: only 8/157 projects (5.1%) have prompt-injection/adversarial/red-team test paths; 97.8% of projects lacking that practice lack it entirely (not partially). This is a corpus-wide, repo-architecture-level confirmation of the same gap Tangent finds at the individual-test level. (source: Dai et al. 2026; Pan et al. 2026)
  • Safeguards exist but don’t travel with the action. Dai et al.: approval, sandboxing, permission, and secret-redaction controls are present in most projects, but coverage is inconsistent across equivalent routes to the same capability (e.g. shell access via CLI vs. via MCP) — the same underlying gap as “no accepted adequacy standard,” expressed architecturally rather than in test counts. (source: Dai et al. 2026)

Tangent’s 23-pattern taxonomy (structure for future pages)

Four categories: test fixtures (mock agent/tool/environment), test data (mocked/real/synthetic/dummy), test objectives (agent/tool, interaction, scenario, e2e), assertions (state/output/memory/reasoning/environment) (source: Pan et al. 2026). A useful checklist against which any new agent-testing technique in this wiki can be positioned.
