Summary: A family of approaches that take a written specification — safety claims, requirements, a skill document, a task description, a formal workflow, an agent’s system prompt and tool definitions — as the source of the tests, the oracle, or the adequacy measure, rather than starting from an arbitrary benchmark.

Core pattern

Four questions recur whenever a specification drives testing:

  1. Which parts of the specification are testable at all? Statements about internals, training, or isolated components cannot be checked through black-box interaction.
  2. Which tests exercise each part? A shared topic is not enough; the mapping from spec element to test has to be explicit.
  3. What counts as pass or fail for that element? The oracle is per-element, not global.
  4. What is left untested? A coverage figure over the specification, kept separate from pass/fail results.

The approaches below answer these differently.

Instances in this wiki

Approach Specification source How tests arise Adequacy / coverage Oracle
LEST (Moshood 2026) Safety claims in model/system cards (natural language) Humans map claims to benchmark seed prompts; mutation operators vary the seeds A claim is covered if ≥1 seed maps to it: 17/29 testable claims, 9/11 refusal-testable Refusal, where the claim makes it applicable; human-validated Refuse→Comply flips
REAG (Wang 2026) Requirements, personas, domain knowledge Retrieved to synthesize executable pass/fail oracles for test scenarios Not the focus Calibrated 3-tier LLM judge cascade with abstention
Skill Coverage (Tan 2026) Constraints extracted from an agent skill document None generated: existing benchmark trajectories are checked Share of documented constraints exercised with observable evidence: 39.90-43.98% on SkillsBench None by design: binary cover/not-cover, independent of task success
Oracle Conversion (Liang 2026) Natural-language requirement for a program (no reference implementation) LLM writes tests (inputs and expected outputs) from the specification Potential kill (input could detect) vs. effective kill (it does, given the predicted output) The model’s own predicted output
Lean4Agent (Wang 2026) Formalized agent workflow specification Not tested: proved before execution, then trajectories checked step by step Structural and semantic predicates Lean-checkable predicates, external validators, LLM judge for natural-language predicates
AgenTest (Quan 2026) A tool-using agent’s system prompt, tool definitions and LLM domain knowledge, mined and refined into Given–When–Then scenarios Generated automatically: a driver builds the database state each Given needs, a simulated user, and a domain-independent interaction strategy None beyond running each refined specification (504 of 551 became test cases) Assertions fixed before execution: deterministic predicates over tool calls and state, plus LLM judgments that must quote the trace

AgentSpec is the runtime counterpart: the specification becomes enforcement rules that block actions during execution rather than a source of tests (see Runtime Enforcement).

What the comparison shows

Coverage of documented behavior is lower than task success suggests

Skill Coverage finds that benchmark runs exercise only about 40-44% of a skill’s documented constraints; LEST finds that 58.6% of prompt-testable safety claims have any applicable benchmark prompt, even though both models pass over 95% of the unmodified prompts. The units differ (constraints in a skill document vs. claims in a system card), so the figures are not comparable as numbers. The shared lesson is that pass rate on a benchmark and coverage of the specification are separate quantities. (source: Tan et al. 2026; Moshood et al. 2026)

The oracle depends on the specification element

LEST shows that a prompt-testable claim does not automatically have a refusal oracle: a claim saying the model occasionally complies with misuse makes a Refuse→Comply flip consistent with the claim. Oracle applicability had the lowest annotator agreement of any LEST step (κ = 0.457). REAG makes a related point from the other side: a generated oracle can itself be wrong, so its judge needs calibration (see LLM-as-Judge Evaluation). (source: Moshood et al. 2026; Wang et al. 2026)

AgenTest splits the oracle by the kind of evidence a specification element has: ownership, argument values and call order become deterministic predicates (492 of 579 default-strategy checks, 85%), while confirmation and disclosure rules get an LLM judgment that must quote the trace. (source: Quan et al. 2026)

Reporting “not covered” apart from “no counterexample”

LEST reports three claim states — not covered, covered with no counterexample observed, counterexample found — and says the middle state is not verification. This keeps absence of failure from being read as presence of coverage, which is the same distinction test adequacy draws between “tests passed” and “tests were sufficient”.

Translation from specification to test: manual in LEST, automated in AgenTest

All of LEST’s claim identification, testability, claim-to-prompt mapping and oracle-applicability judgments were manual (three annotators, κ 0.457-0.912). In REAG, retrieval precision rather than oracle generation quality is the dominant bottleneck for oracle correctness. Both identify automating the specification-to-test step as the open problem. (source: Moshood et al. 2026; Wang et al. 2026)

AgenTest automates the step end to end for tool-using agents: LLM-mined specifications, a driver that builds the database state and simulated user each Given needs, and oracle assertions fixed before execution. The cost moves to specification correctness: 88.0% of its 551 refined specifications were correct (80.6% of those inferred from domain knowledge), and the 66 wrong ones (30 unsupported by the source, 19 contradicting it, 17 missing a condition of the rule) include 26 of the 47 specifications for which no test driver could be built. (source: Quan et al. 2026)

The specification may have to be mined, and mined rules are the least reliable

AgenTest’s agents come without a requirements document. Tool definitions and domain knowledge supply 56% of the retained specifications, and rules stated in no artifact account for 50.6% (DeepSeek-V4-Flash) and 36.4% (Qwen-3.8-Flash) of the bugs found, including almost all unauthorized-action bugs (8 of 9 and 9 of 10). The first question above (“which parts are testable at all?”) also shows up here: 21 specifications could not be tested because the environment cannot hold the state they assume. (source: Quan et al. 2026)
