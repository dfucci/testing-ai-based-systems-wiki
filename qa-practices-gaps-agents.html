Summary: Repository-artifact study of 157 open-source LLM-agent projects (≥100 GitHub stars) coding QA evidence across four layers — execution surfaces, safeguards, testing artifacts, risk scenarios — and finding that safeguards exist but are applied inconsistently across equivalent action routes, while agent-specific testing (adversarial, untrusted-context, multi-step) is nearly absent.

Sources:

  • Dai et al. - 2026 - A Large-Scale Empirical Study of Quality Assurance Practices and Gaps in AI Agents.pdf (arXiv:2609.17698v1, 15 Sep 2026)

Last updated: 2026-10-18

Motivation

Agent QA has to ask a question conventional LLM-application QA doesn’t: are model-influenced actions (shell commands, file writes, browser navigation, subagent delegation, API calls) bounded, not just whether model outputs are correct. Prior agent-security work (ToolEmu, AgentDojo, AgentSecurityBench) studies attacks/defenses in controlled environments; this paper instead asks what QA practice actually looks like across real, popular open-source agent repos. (source: Dai et al. 2026)

Method

157 GitHub repos (≥100 stars as of May 2026), filtered from 5,852 raw hits, each integrating an LLM/model-compatible API with an executable entry point and ≥1 model-mediated action surface (shell, file, browser, MCP/plugin, persistent state). Corpus: SWE automation 26.8%, personal/multichannel assistants 19.7%, coding assistants 19.1%, research/information agents 13.4%, browser/computer-use automation 12.1%, domain-specific 8.9%. Reviewers manually coded repository-visible artifacts (docs, source, config, tests, deployment files) against an inductively-developed four-layer rubric; labels record that a reviewable mechanism/test exists, not that it is runtime-effective. No inter-rater agreement was computed (open coding refined through reviewer consensus, not a fixed codebook).

Four-layer coding rubric

  • Execution surfaces — where the agent can act or be invoked: UI, CLI, API, browser, filesystem, shell, plugin, MCP.
  • Safeguards — mechanisms constraining, validating, or monitoring model-mediated actions: approval/authorization, sandboxing/isolation, permission/policy controls, secret management/redaction, MCP/plugin registration, browser/domain scoping.
  • Testing artifacts — tests, evaluations, benchmarks, reproduction scripts, security tests, failure-oriented checks.
  • Risk scenarios — end-to-end chains where untrusted input or model-mediated decisions may reach a sensitive action, asset, or persistent state. Coded as candidate review situations, not confirmed vulnerabilities.

RQ1 findings: what QA practice is visible

Execution surfaces (RQ1.1)

Every surface family shows near-universal presence of some control, but coverage is inconsistent across overlapping routes: a project (e.g. google-gemini/gemini-cli) may expose CLI, shell, filesystem, browser, web, and MCP paths, each requiring separately-verified controls. Named recurring challenges: inconsistent control across overlapping action paths (96.8% of projects), outbound network/API effects beyond project boundary (99.4%), credential leakage through configuration (98.7%), workspace escape through file access (97.5%), host process/environment modification via commands (94.3%), extension-driven authority expansion via MCP/plugins (80.9%), unreviewed runtime code execution (78.3%), browser session/cross-domain exposure (75.8%).

Practice families used to address these: approval/authorization controls, sandboxing/isolation, permission/policy controls, secret management/redaction, MCP/plugin registration and configuration, browser/domain-scoping controls.

Safeguards (RQ1.2)

Practices are widely present, but the real issue is context-sensitive coverage: the same agent capability may be treated as acceptable in one setting and risky in another, so the safeguard has to travel with the action, not the surface. Same six challenge categories recur (privileged command execution, file/workspace boundary, secrets/credentials, plugin/MCP authority, browser session/domain scoping) at 75.8-98.7% of projects each.

Testing artifacts (RQ1.3)

Across all 157 projects: 87.3% have conventional tests/specs, 60.5% security/safety-oriented tests, 49.7% evaluation/benchmark/adversarial/red-team-like paths, but only 8 projects (5.1%) have prompt-injection/adversarial/jailbreak/red-team testing paths specifically. Conventional tests catch ordinary regressions (parsing, session state, API wrappers); they don’t test whether a model-mediated action crosses a boundary it shouldn’t. This is the sharpest quantitative gap in the paper.

Risk scenarios (RQ1.4)

Eight risk-chain templates, each an end-to-end path from untrusted input/model decision to a sensitive action or asset:

Risk chain Projects showing it
Secret-to-tool 94.9%
Workspace-to-persistent-state 81.5%
Extension-to-authority 87.3%
Mode-switch-to-privilege 78.3%
Runtime-code 63.1%
Model-to-process 83.4%
Session-to-action 38.2%
Untrusted-context-to-action 28.7%

Two practice categories interrupt these chains: chain-interruption (approval at the privileged-action transition, sandboxing to contain execution/state effects, secret-redaction to stop propagation) and systematic risk-avoidance (scoping allowed paths/tools/modes upfront, making extension/runtime authority reviewable, scoping browser sessions/domains). Design-time avoidance and interruption-at-critical-points dominate; few projects show both.

RQ2: undercovered QA problems

Table VI (source) reports the largest gaps by dimension — the % of projects exposing a challenge but lacking its matched direct practice:

  • Execution surfaces: secret management/redaction missing in 36.1% of projects exposing credential-relevant routes; sandboxing/isolation missing in 30.1-30.4% of file-access/command-execution routes.
  • Safeguards: same gap pattern (36.1% secret handling, 30.1% file/workspace containment, 27.1% MCP/plugin extension control, 26.9% browser/session scoping) — broad controls exist but don’t always bind to the specific action that needs them.
  • Testing artifacts: the largest gaps in the whole paper — 97.8% of projects lacking adversarial/untrusted-context tests lack them entirely; 52.4% lack eval/red-team-like paths; 39.7% lack security/safety-oriented tests.
  • Risk scenarios: 35.6% of projects with a credential-flow risk chain have no matched secret-management practice; 30.5% of command-execution-risk projects lack sandboxing/isolation; 29.7% of file-boundary-risk projects likewise; 26.3% lack MCP/plugin registration review.

The paper’s synthesis: undercovered QA is agent-specific, not classic software defects — model-mediated tool use, session reuse, extension authority, and untrusted-context propagation systematically lack matching QA artifacts beyond ordinary tests, access checks, or config review.

Recommendations (source)

  1. Define controls by protected action or asset (a secret, a file, a shell boundary, a browser domain), not by interface — so the same boundary applies whether the route is CLI, API, MCP, browser, or headless/batch.
  2. Every high-authority route or risk chain should have a failure-oriented test or replay case that fails when the required approval, sandbox, policy, redaction, domain-scope, or extension check is removed.

Relation to existing wiki content

Complements LLM Agent Testing Practice (Tangent + Magalhães): those studies characterize what agent tests look like as written artifacts (shallow, unit-dominated, reasoning-untested); this study characterizes what agent QA coverage looks like at the repository-architecture level (execution surfaces × safeguards × risk chains), largely independent of test quality. The 5.1% adversarial-test figure here is a harder, corpus-wide version of Tangent’s 7.5%-NFR-tests finding — both converge on: agent-specific, boundary-crossing failure modes are almost never tested for, regardless of framework or project category.

Overlaps Agent Safety’s risk taxonomy (AgentSpec’s code-execution/embodied/AV risk categories) but at a different level: AgentSpec studies runtime enforcement effectiveness for a fixed rule set; this paper studies repository-visible evidence of intent to enforce, across a much larger, more heterogeneous corpus, without validating runtime effectiveness.
