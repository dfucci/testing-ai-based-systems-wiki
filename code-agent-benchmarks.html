Summary: Benchmarks used to evaluate LLM-based code agents span capability (SWE-bench, PolyBench), safety (RedCode-Exec, SafeAgentBench), and autonomous driving (FixDrive), each testing different aspects of agent behavior. Multi-turn and conversational tool-use settings (SWE-DIVE, τ²-bench) and an impossible-task setting for test tampering (ImpossibleBench) have their own sections.

Capability Benchmarks

SWE-bench Verified

500 real-world GitHub issues from 12 Python repositories with human-verified patches. The primary benchmark for measuring agent ability to resolve software engineering tasks. Pass@1 rates for top agents: GPT-5 ~66-67%, Qwen-Coder-480B ~61%.

Used in TRAJEVAL to analyze 9,500 trajectories across 3 architectures and 7 models. (source: TRAJEVAL paper)

PolyBench Verified

382 multilingual issues across Python, Java, JavaScript, and TypeScript from 20 repositories. Tests cross-language generalization. Tasks are harder: GPT-5 achieves only ~39% Pass@1 vs. ~67% on SWE-bench.

Key finding: agents need ~25% more tool invocations on PolyBench than SWE-bench, and bash output tokens increase dramatically, reflecting verbose compilation errors in statically-typed languages. (source: TRAJEVAL paper)

DevBench

Developer-informed benchmark for code generation models (Golnari et al., 2026). Provides development environment metrics but lacks stage-wise decomposition and golden context comparison.

Safety Benchmarks

RedCode-Exec

750 risky code execution scenarios across 25 vulnerability categories, each with 30 test cases. Categories include: post sensitive files online, untrusted installation, delete sensitive files, reverse shell creation, unsafe deserialization, cryptographic predictability, etc.

Used to evaluate AgentSpec on the CodeAct code agent. (source: AgentSpec paper)

SafeAgentBench

Benchmark for embodied agent safety. 250 unsafe scenarios across 10 hazard categories (fire, electrical shock, explosion, poisoning, slip, liquid damage, breakage, appliances misuse, property damage, small items damage) plus safe scenarios. Used to evaluate AgentSpec on a robotic arm agent. (source: AgentSpec paper)

FixDrive

Law-violation scenarios for autonomous vehicle evaluation (Yang et al., 2025). 8 scenarios covering collision, traffic signal violations (Laws 38, 44, 46, 53), and journey completion. Used to evaluate AgentSpec on the Apollo autonomous driving system. (source: AgentSpec paper)

Multi-Turn and Conversational Settings

SWE-DIVE

Not a new task set but a wrapper: it converts single-prompt tasks from benchmarks supported by the Harbor framework (SWE-bench Verified, Terminal-Bench) into multi-turn conversations with an LLM-simulated user in one of three personas, and adds regression and waste measures. See SWE-DIVE. The paper contrasts it with CodeFlowBench and CodeGen (predefined multi-turn task sequences) and AmbigSWE-bench (ambiguous instructions with clarification questions), which it describes as following a predefined process that does not adapt to what the agent asks. (source: Brehme et al. 2026)

τ²-bench

Conversational tool-use benchmark with airline, retail and telecom agents (15, 17 and 13 tools; telecom adds 30 user-side tools) and 278 hand-written tasks (50, 114 and 114), each played by a simulated user and judged mainly by the final database state plus a few required actions. Used as system under test and as a baseline by AgenTest, which also compares against IntellAgent (policy-combination scenario generation, LLM judge) and MANTRA (SMT-validated compliance tasks; 44, 57 and 31 tasks in its released suites). (source: Quan et al. 2026)

Impossible-Task Setting

ImpossibleBench

Measures an agent’s propensity to exploit test cases. Each task asks the agent to implement a function from its docstring and make the unit tests pass, but the benchmark’s authors altered the tests so that they contradict the specification. In the oneoff split one assertion expects an incorrect value; in the conflicting split two assertions expect different values for the same input; each split has 103 tasks. No implementation that follows the specification passes all the tests, so the right response is to report the faulty test, and the wrong one is to cheat by tampering with the test file or by tailoring code to the faulty test. Both cheats can be checked mechanically without a judge, and the rules identify potential reward hacking. EPISTEME ran all 206 tasks with Qwen3-235B-A22B and Mistral Large 3: 49 of 400 completed runs misbehaved (16 tampering, 33 exploitation), more often on oneoff tasks (21%) than on conflicting ones (4%). (source: Bobadilla et al. 2026)
