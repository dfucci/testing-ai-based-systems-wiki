Testing the Untestable? An Empirical Study on Testing LLM-Powered Software (Magalhães et al. 2025)

Summary: Qualitative case study of 21 student teams building real LLM-integrated apps (99 reflection reports, thematic analysis) showing how developers blend traditional and model-aware testing strategies to cope with non-determinism and the oracle problem.

Sources: Magalhaesetal2025.pdf

Last updated: 2026-08-19

Motivation

LLM-powered systems are increasingly core components in real applications, but non-deterministic, prompt-sensitive, drift-prone behavior breaks standard testing assumptions (e.g. regression-test reliability). Existing literature evaluates model performance in isolation, not how full systems integrating LLMs are actually tested during development. (source: Magalhães et al. 2025)

Method

Exploratory/descriptive qualitative case study (Runeson & Höst methodology) analyzing 99 individual student reflection reports from 21 team projects in a third-year undergraduate software architecture course — teams built and publicly deployed real LLM-integrated apps (SQL persistence, mandatory LLM feature). Hybrid human+GPT-4.0-assisted thematic analysis across four dimensions: type of testing, LLM behavior, testing challenges, lessons learned, verified by two researchers.

Findings

See LLM Agent Testing Practice for synthesis against Tangent’s independent large-scale study. Headline points:

  • Testing/coding stayed rooted in source-code analysis even for LLM components (backend debugging, parsing, API integration).
  • Teams used hybrid strategies: manual exploratory, manual ad hoc, manual scripted, and automated unit/integration testing combined with model-aware/behavior-based evaluation — no single strategy sufficed.
  • LLM unpredictability (non-determinism, prompt sensitivity, hallucinations) forced fallback logic, retries, and tolerance-based/qualitative pass criteria rather than strict pass/fail oracles.
  • Challenges ranked by source-code coupling: integration issues, non-deterministic behavior, prompt engineering difficulties, hallucinations, output imbalance/bias risk.

Limitation

Participants are students in a simulated setting, not professional developers — findings are transferable but not statistically generalizable to industry practice. (Tangent’s independent, industry-grounded study reaching similar conclusions is a useful corroboration despite this limitation.)
