Summary: AgentSpec is a domain-specific language (DSL) that lets users define runtime enforcement rules for LLM agents, intercepting unsafe actions before they execute across code, robotic, and autonomous vehicle domains.

Sources: Wang et al. - 2025 - AgentSpec Customizable Runtime Enforcement for Safe and Reliable LLM Agents.pdf

Last updated: 2026-10-18

Overview

LLM agents operating autonomously can take harmful, unintended actions — financial transactions, destructive file operations, traffic law violations. AgentSpec provides a declarative mechanism for constraining agent behavior at runtime without modifying the agent’s internals. (source: Wang et al. 2025)

Unlike post-hoc evaluation (e.g., TRAJEVAL) or pre-execution risk estimation, AgentSpec enforces constraints during execution at specific decision points.

The AgentSpec Language

Each rule has five parts (source: Wang et al. 2025): 

rule <id>
  trigger <Event>
  check <Pred>*
  enforce <Enforce>+
end

Triggers

Events that activate a rule:

  • General: statechange, beforeaction, agentfinish
  • Code (PythonREPL): execution events
  • Robotic: find, pick, put, open, close, pour, throw, etc.
  • ADS: redlightdetected, enteringroundabout, pedestriandetected, etc.

Checks (Predicates)

Boolean conditions evaluated when trigger fires. Can be:

  • Manually defined Python functions (e.g., is_destructive_cmd, is_fragile_object)
  • Automatically generated by an LLM given domain context

Enforcement Actions

Actions taken when trigger fires and all predicates hold:

  • stop — terminate agent execution
  • user_inspection — pause and prompt user to approve/reject
  • llm_self_examine — invoke self-reflection to generate corrective action
  • invoke_action(params) — execute a predefined corrective action

Implementation

AgentSpec is implemented for LangChain by intercepting iter_next_step (source: Wang et al. 2025). Three hook points:

  1. AgentAction — before an action executes
  2. AgentStep — after an action produces an observation
  3. AgentFinish — when the agent completes its task

The framework is architecture-agnostic: the same principles apply to AutoGen and Apollo autonomous driving systems.

Evaluation Results

RQ1: Expressiveness and Effectiveness

Evaluated on three agent types (source: Wang et al. 2025):

Agent Dataset Result
Code (CodeAct) RedCode-Exec (750 risky scenarios, 25 categories) >90% unsafe executions prevented
Embodied (robotic arm) SafeAgentBench (250 scenarios, 10 hazard categories) 100% hazardous actions eliminated
Autonomous vehicle (Apollo) FixDrive (8 law-violation scenarios) 100% law compliance in tested scenarios

Safe task success drops only slightly for embodied agents (58.62% → 54.26%).

RQ2: LLM-Generated Rules

Using OpenAI o1 to auto-generate AgentSpec rules (source: Wang et al. 2025):

  • Code agent: 87.26% of risky code enforced (25 rules generated from 750 scenarios); failures mostly from rules over-fitting to the in-context examples rather than generalizing
  • Embodied agent: 95.56% precision, 70.96% recall (10 rules for 250 scenarios); false negatives from rules missing complex object properties (e.g. failing to recognize a lit candle as already lit)
  • AV (zero-shot): 5 out of 8 law-breaking scenarios prevented (62.50%); missed Law38 (traffic-light response) and Law46 (speed limit under fog/rain)

LLM-generated rules tend to over-fit to provided examples and may miss broadly-stated requirements.

RQ3: Rule Generalizability

Single rules cover many instances: one embodied-agent rule (Figure 7 in paper) prevents 96 risky scenarios. Rules share predicates across risk categories. (source: Wang et al. 2025)

RQ4: Runtime Overhead

Component Overhead
Parsing ~1.42 ms
Predicate evaluation (code) ~2.83 ms
Predicate evaluation (embodied) ~1.11 ms

Negligible relative to agent execution times (~25.4s for code agents, ~9.82s for embodied agents). (source: Wang et al. 2025)

Limitations

  • Deterministic enforcement only: no probabilistic or trajectory-based safety analysis; cannot reason about long-term consequences of current actions
  • No future-state estimation: cannot detect when immediate preconditions are safe but risky states are likely later
  • Future work: DTMC-based probabilistic reachability queries

(source for this section: Wang et al. 2025)
