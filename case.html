Summary: CASE labels retrieved software artifacts (code, tests, pull requests, architecture documents) as valid, invalid or unknown for a given deployment and time, using feature-flag, configuration and migration evidence, and packages them for a coding agent as act-on, explain or verify. A synthetic pilot of six tasks, 15 artifacts and three deployments gives CASE precision and recall of 1.00 against reference labels that follow CASE’s own rules, and no coding agent was run.

Sources:

  • Assunção and Periyathambi - 2026 - When Relevant Code Is Wrong Runtime-Aware Context for AI Coding Agents.pdf (arXiv:2610.38800v1, 28 Oct 2026; North Carolina State University and eBay)

Last updated: 2026-11-08

Problem

Coding agents retrieve code, pull requests (PRs) and documentation to guide a change. Conventional retrieval estimates topical relevance R(a, q) of an artifact a to a task q, by lexical matching (BM25), semantic similarity or repository graphs. In large, evolving systems several implementations, architectural versions and runtime configurations coexist, so a highly relevant artifact can describe an implementation that is inactive or incompatible with the target deployment. The authors’ point is that relevant information is not necessarily applicable information, and that an agent can then propose a plausible change that is incompatible with the system’s operational state. They cite earlier work showing that retrieved repository context can be temporally stale and induce obsolete API usage. (source: Assunção and Periyathambi 2026)

Operational context validity

For a task q, a target system snapshot t, a deployment context d (for example a region with its regulations, enabled flags, service versions and rollout cohort) and a candidate artifact a, the paper defines applicability as

  • valid if the timestamped evidence Et entails the preconditions πa(d) under which the artifact’s implementation applies;
  • invalid if Et entails their negation;
  • unknown otherwise. (source: Assunção and Periyathambi 2026)

Et comes from deployment manifests, flag configurations, service routing and migration records. A definitive label needs sufficiently authoritative, non-conflicting evidence; missing or contradictory evidence yields unknown. Absence from sampled production logs alone cannot establish that a path is disabled. Each applicability assertion should carry its source, timestamp, scope and any unresolved conflict. (source: Assunção and Periyathambi 2026)

Validity is kept separate from relevance. A migration PR can have high relevance but be invalid for implementing the current path, and can still be included as labeled historical rationale; labels say whether an artifact can guide an implementation decision, not whether its content was ever correct. A commit date is only a clue, and the same old REST endpoint can be invalid for one deployment and valid for another at the same time (a regional rollback). The paper’s stated core hypothesis, untested in the pilot: holding model, candidate pool and context-token budget constant, packages that distinguish valid, invalid and unknown artifacts reduce deployment-incompatible implementation decisions compared with similarity-only retrieval, with gains concentrated in systems with architectural migrations or configuration-dependent execution. (source: Assunção and Periyathambi 2026)

The CASE framework

Three steps, described for an existing agent that receives the result through its normal context interface (no fine-tuning or autonomous production change assumed). (source: Assunção and Periyathambi 2026)

  1. Reconstruct context. From a top-k repository/PR retrieval pool, build a small versioned context graph. Nodes are artifacts, implementations, flags, deployments and services; edges are guards, deployed-in, calls and supersedes. Links come from configuration exports, service inventories, PR metadata and a limited set of developer-verified mappings.
  2. Evaluate applicability. Label each candidate valid, invalid or unknown with explicit provenance. Unknowns stay visible and may trigger a question or more retrieval. A flag-guarded implementation counts as applicable only when its activation conditions are supported, because flags can depend on cohorts and live rollouts.
  3. Package evidence under a token budget. Each actionable claim has an artifact pointer, applicability scope, evidence timestamp and status. The package sorts artifacts into ACT ON (applicable code and tests), EXPLAIN (obsolete decisions kept as historical rationale) and VERIFY (unresolved constraints).

Pilot evaluation

Setup

An illustrative merchant-trust application in Java with Spring Boot exposes a trust score through a legacy REST endpoint and a newer GraphQL architecture. The U.S. deployment migrated to GraphQL, the European deployment rolled back to REST, and the Asia-Pacific deployment has a partially enabled GraphQL configuration with unresolved cohort information. The fixture has 15 artifacts (source code, tests, historical PRs, architecture documents), three deployments and six tasks: two architectural migrations, two feature-flag/regional variations and two stable components. Each task fixes a deployment and a time. BM25 returns the top eight candidates per task, and all conditions share a budget of about 1,500 tokens. (source: Assunção and Periyathambi 2026)

Four conditions: Semantic Only; Recency Filtered (180-day window); Semantic + Raw Configuration (deployment configuration added without assessing applicability); and CASE. Two ablations remove feature-flag evidence or architectural lineage. Metrics are valid precision (share of actionable artifacts that are applicable), valid recall (share of applicable artifacts in the pool kept as actionable), and the numbers of incompatible and unknown artifacts presented as actionable. For conventional retrieval every retrieved artifact is actionable; for CASE only ACT ON artifacts are. Precision and recall are task means; the results are a deterministic replay. (source: Assunção and Periyathambi 2026)

Results

Condition Precision Recall Incompatible actionable Unknown actionable
Semantic Only 0.50 1.00 16 5
Recency Filtered 0.43 0.43 6 5
Semantic + Raw Cfg. 0.50 1.00 16 5
CASE 1.00 1.00 0 0
CASE w/o Flags 0.33 0.13 0 0
CASE w/o Lineage 1.00 1.00 0 0

Incompatible and unknown counts are total actionable artifact occurrences over the six tasks. (source: Assunção and Periyathambi 2026, Table I)

  • Relevance versus validity. Semantic retrieval finds every applicable artifact (recall 1.00) but only half of what it presents as actionable is applicable. Recency filtering cuts incompatible occurrences to six but drops recall to 0.43; after the European rollback to REST, all four artifacts it kept for that task were incompatible.
  • Explicit classification. CASE presents no incompatible or uncertain artifact as actionable. Adding raw configuration without classification leaves the selection identical to semantic retrieval.
  • Runtime evidence. Removing feature-flag evidence lowers recall from 1.00 to 0.13, because artifacts that are actionable with flag evidence become uncertain without it. Removing lineage changes nothing in this fixture because the flags already determine the applicable paths. Replaying identical requests against different deployments, CASE switches its actionable context from the GraphQL implementation in us-prod to the REST implementation in eu-prod.

Scope of the evidence

The authors call the pilot a feasibility evaluation rather than an independent assessment of effectiveness. Limits stated by the paper or visible in its table (source: Assunção and Periyathambi 2026):

  • Circular reference labels. The fixture is synthetic, artifact relationships and applicability conditions are manually curated, and the reference labels follow the same rules the CASE evaluator implements. The authors say the perfect precision and recall are expected under the fixture’s assumptions and should not be read as evidence of generalization.
  • Context selection only. No coding agent was run. The pilot measures which artifacts are presented as actionable, not the correctness of agent decisions or generated patches. Whether an agent could infer applicability from raw configuration by itself is left open.
  • One uninformative baseline. The Semantic + Raw Configuration row equals Semantic Only on every column, because the raw configuration is not used to classify artifacts.
  • Lineage untested. The lineage ablation has no effect in this fixture, so the architectural-lineage component is not exercised by the pilot.
  • Small and single-domain. Six tasks, 15 artifacts, one application; the paper reports one deterministic replay and no variance.
  • Unevaluated hypothesis. The core hypothesis about fewer incompatible implementation decisions is not tested.

The authors’ plan is independently annotated development tasks and controlled experiments against conventional retrieval, recency filtering and simpler configuration-aware alternatives at equal context budgets, assessing context-selection quality and downstream outcomes (implementation planning, patch correctness, deployment compatibility), plus incomplete or conflicting evidence and the trade-offs among accuracy, abstention, retrieval cost and scalability.

Relation to the rest of the wiki

Golden Context defines the code elements an agent must find from a SWE-bench task’s reference patch (Kim et al. 2026); CASE instead decides, from deployment and flag evidence, which retrieved artifacts may guide a change to a given deployment. Both concern which context should guide a code agent, in different settings. The CASE paper evaluates context selection and does not test or verify agent output.
