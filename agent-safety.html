Problem Space

LLM agents operating autonomously introduce safety risks that differ from traditional software:

  • Emergent behavior: agents may take sequences of individually plausible actions that collectively produce harmful outcomes
  • Misaligned intent: autonomous decision-making can diverge from user expectations in novel situations
  • Irreversibility: destructive file operations, financial transactions, physical actions (robotic, AV) cannot be undone
  • Domain diversity: the same agent technology is deployed in code execution, healthcare, finance, robotics, and autonomous vehicles — each with different risk profiles

Safety Risk Taxonomy

From the AgentSpec evaluation (source: Wang et al. - 2025):

Code execution risks: posting sensitive files online, untrusted installation, crawling risky websites, copying/listing sensitive files, writing risky content, delete operations, reverse shell creation, side channel vulnerabilities, unsafe deserialization, cryptographic predictability

Embodied agent risks: fire hazard, electrical shock, explosion, poisoning/ingestion, slip hazard, liquid/spill damage, breakage and dropping, appliances misuse, property damage, damage to small items

Autonomous vehicle risks: collision, traffic law violations (red light, speed, lane laws)

Approaches to Safety

Pre-execution risk assessment

LLM-based sandboxes (e.g., ToolEmu) simulate potential outcomes before execution. Identifies risks but offers no enforcement mechanism; susceptible to adversarial manipulation.

Rule-based runtime enforcement

Runtime enforcement systems like AgentSpec enforce predefined constraints at execution time. High reliability (>90% unsafe execution prevention) but requires rule specification effort.

Training-time alignment

Model fine-tuning and RLHF aim to make models refuse unsafe instructions. Does not generalize reliably across deployment contexts; susceptible to jailbreaking.

Post-hoc evaluation

Trajectory analysis tools like TRAJEVAL identify what went wrong. Useful for diagnosis and iterative improvement but reactive rather than preventive.

Key Empirical Results

From AgentSpec evaluation:

  • >90% of unsafe code executions prevented
  • 100% of hazardous embodied agent actions eliminated (across 10 hazard categories)
  • 100% AV law compliance in FixDrive scenarios
  • Safe task success rate drops only slightly: 58.62% → 54.26% for embodied agents

The safety–capability trade-off appears manageable: significant safety gains at modest capability cost.

LLM-Generated Safety Rules

AgentSpec demonstrates LLMs can auto-generate safety rules from domain descriptions. OpenAI o1 achieves:

  • 95.56% precision (rarely flags safe actions as unsafe)
  • 70.96% recall (misses ~29% of risky scenarios)

The precision-recall asymmetry means LLM-generated rules are conservative but incomplete. Manual rules needed for comprehensive coverage.

Repo-Level QA Evidence (Dai et al. 2026)

AgentSpec’s risk taxonomy above is enforcement-focused: a fixed rule set applied at runtime. Dai et al. 2026 instead surveys repository-visible evidence of safety intent across 157 popular open-source agent projects, without validating runtime effectiveness. It reframes safety risk as eight end-to-end risk chains (untrusted input or model decision → sensitive action/asset/persistent state): secret-to-tool, workspace-to-persistent-state, extension-to-authority, mode-switch-to-privilege, runtime-code, model-to-process, session-to-action, untrusted-context-to-action.

Two practice families interrupt these chains in practice: chain-interruption (approval at the privileged-action transition, sandboxing to contain execution/state effects, secret-redaction to stop propagation) and systematic risk-avoidance (scoping allowed tools/modes upfront, reviewable extension/runtime authority, scoped browser sessions). Coverage is broad but inconsistent: the same safeguard family (e.g. secret management) is missing for 26-36% of projects exposing the matching risk chain, and only 5.1% of all 157 projects have any adversarial/red-team test path — safeguards exist more often than tests that would catch their removal or bypass.

Key implication for this page’s framing: safety mechanisms should be bound to the protected action or asset, not the interface — the same boundary (a secret, a file, a shell command) needs to hold whether the route in is CLI, API, MCP, or browser, which AgentSpec-style rule sets don’t guarantee unless rules are written per-route.

Testing a model’s own documented safety claims (Moshood et al. 2026)

The approaches above concern agent actions. LEST tests a different layer: the safety claims a provider publishes for a model in its system card (refusal of harmful requests, avoiding encouragement of self-harm, avoiding stereotyped outputs). Only 29 of 56 claims across the Claude Opus 4.8 and GPT-5.5 system cards were prompt-testable through black-box interaction; both models refuse over 95% of unmodified SORRY-Bench seed prompts, yet human-validated Refuse→Comply flips under mutated prompts contradict 6 of the 9 covered refusal-testable claims. See Specification-Based Testing. (source: Moshood et al. 2026)

System-level and business-rule evidence (Zheng et al. 2025; Quan et al. 2026)

AgentSight demonstrates detection of an indirect prompt injection at the system boundary: an agent told to build a C project follows a README link to a page with a hidden prompt, then sends /etc/passwd to an external server in a command disguised as a build step. The system captured the chain (521 raw events merged into 37) and an observer LLM rated it a high-confidence attack. This is one constructed case, without detection rates. AgenTest finds a different safety-relevant violation without any adversary: in benign, specification-driven conversations the tool-using agents acted on another user’s objects (9 violated specifications on DeepSeek-V4-Flash, 10 on Qwen-3.8-Flash), almost always because no artifact stated the ownership rule. Both are action-level risks that a task-success metric would not flag. (source: Zheng et al. 2025; Quan et al. 2026)

Open Problems

  • Long-term consequence reasoning: current enforcement is local (immediate action) rather than trajectory-level
  • Rule completeness: unknown unsafe scenarios have no rules; coverage gap is inherent
  • Adversarial robustness: rules can be defeated by prompt injection or context manipulation
  • Cross-domain generalization: rules designed for one domain may not transfer
